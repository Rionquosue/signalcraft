# Relay bot protocol — specification sheet

Protocol 1.0 • 22 October 2026 • Proposed HTTP interface

## Purpose

Some destinations are reached through a bot you run, not through a social platform's public API. This protocol defines how the Rails application hands a scheduled post to such a bot and learns whether it was delivered. Two addons use it:

| Addon | Relay | Mode |
|---|---|---|
| 2 - 9 Discord (02-9) | Your self-hosted YAGPDB fork with the `socialpub` plugin | Push |
| 2 - 10 Telegram (02-10) | Your own Telegram bot, built later | Push or pull |

The Rails side is one shared relay addon base used by both addons; each addon adds its destination's limits and options. The relay side is whatever bot implements this protocol.

## Concepts

| Term | Meaning |
|---|---|
| Relay | The bot service that posts messages (YAGPDB fork, Telegram bot) |
| Link | One connection between a Rails workspace and a relay, with its own tokens |
| Destination | One place the relay posts to: one Discord channel or one Telegram chat. Each destination is one social account in Rails, with its own queue and schedule. |
| Delivery | One request to post one publication target to one destination, identified by its idempotency key |

## Modes

| Mode | Who connects to whom | Use when |
|---|---|---|
| Push | Rails worker calls the relay's HTTPS API | The relay can accept inbound connections from Rails (same Docker network, or reachable over HTTPS). YAGPDB uses this. |
| Pull | The relay calls Rails to collect due deliveries and report results | The relay cannot accept inbound connections, for example a Telegram bot running long polling on another machine |

A destination uses one mode, chosen when it is connected.

## Authentication

| Direction | Credential | Stored as |
|---|---|---|
| Rails → relay (push) | `Authorization: Bearer <relay_token>` | Rails: encrypted in the social account's credentials. Relay: SHA-256 digest only. |
| Relay → Rails (pull) | `Authorization: Bearer <rails_token>` | Relay: its secret configuration. Rails: SHA-256 digest only (`integration_tokens`). |

- Tokens are at least 256 bits of random data, encoded base64url, generated by the side that will verify them and shown once.
- Every request uses HTTPS, except between containers on a private Docker network that the operator has declared trusted.
- Each token is bound to one link. A relay token grants access only to that link's destinations; a Rails token grants access only to that link's deliveries.
- Rotation: the verifying side issues a second token; both are accepted until the old one is revoked.
- Replayed requests are harmless: every write is idempotent by `idempotency_key`.
- Tokens never appear in URLs, logs or error messages.

## Common rules

- JSON bodies, UTF-8, `Content-Type: application/json`. Unknown request fields are rejected with 422; clients ignore unknown response fields.
- Times are RFC 3339 UTC. Sizes are integer bytes.
- Errors use one shape:

```json
{ "error": { "code": "destination_forbidden", "message": "The bot cannot post in this channel.", "retryable": false, "delivery_state": "not_submitted" } }
```

- `delivery_state` is `not_submitted`, `submitted` or `unknown`, with the same meaning as in 04, so Rails knows whether a retry could post twice.
- `429` and `503` include `Retry-After`.
- Breaking changes use a new path version (`/relay/v2`).

## Push mode: endpoints the relay provides

Base: the relay URL entered when connecting, for example `https://yagpdb.example.org/relay/v1`.

### GET /destinations/{destination_id}

Used when connecting and whenever Rails refreshes capabilities (at least daily).

```json
{
  "destination_id": "dst_7Q2...",
  "kind": "discord_channel",
  "display_name": "#news",
  "container_name": "Studio Community",
  "can_post": true,
  "problem": null,
  "limits": {
    "max_text_chars": 4000,
    "max_attachments": 10,
    "max_attachment_bytes": 10485760,
    "media_types": ["image/jpeg", "image/png", "image/gif", "image/webp", "video/mp4"]
  },
  "options": ["mention_role_ids", "publish_announcement", "suppress_link_previews"]
}
```

`can_post: false` comes with `problem` (`missing_permission`, `channel_missing`, `bot_removed`, `chat_not_found`). Rails then blocks that account's targets with reason `account_disconnected` and shows the problem.

### POST /deliveries

```json
{
  "idempotency_key": "4b9d0e0a6f6c4f1e9d4b7a2e1c0f3a55",
  "destination_id": "dst_7Q2...",
  "text": "Small details. Better workflows.\nhttps://app.example.org/r/Xy7Pq2LmNa",
  "text_format": "plain",
  "media": [
    {
      "position": 0,
      "content_type": "image/jpeg",
      "byte_size": 482113,
      "sha256": "9f2c...",
      "alt_text": "A desk with the new prototype.",
      "filename": "image-1.jpg",
      "fetch_url": "https://app.example.org/integrations/discord_yagpdb/relay/media/kT3...",
      "fetch_expires_at": "2026-10-23T13:30:00Z"
    }
  ],
  "options": { "mention_role_ids": ["123456789012345678"], "publish_announcement": true },
  "scheduled_for": "2026-10-23T13:00:00Z",
  "target_ref": "pt_01J..."
}
```

- `text` is final: tracked links are already substituted. The relay posts it as plain text and must not shorten or rewrite links. `text_format` is always `plain` in v1.
- `fetch_url` is a single-delivery media URL on Rails. It needs no other credentials, expires after 1 hour by default, can be fetched repeatedly until then, and serves exactly the bytes whose SHA-256 is given. The relay verifies size and hash before posting. Media is never sent inline in the JSON.
- `options` may only contain options the destination listed.

Responses:

| Status | Meaning |
|---|---|
| 202 `{ "status": "queued" }` | Accepted; poll the delivery |
| 200 with a delivery resource | Already finished (repeat of a completed key) |
| 409 `idempotency_conflict` | Same key, different body |
| 422 | Validation failed (`text_too_long`, `too_many_attachments`, `attachment_too_large`, `unsupported_media_type`, `unknown_option`) |
| 403 `destination_forbidden` / 404 `destination_not_found` | Destination not usable by this link |

The relay keeps each idempotency key and its result for at least 14 days.

### GET /deliveries/{idempotency_key}

```json
{
  "idempotency_key": "4b9d0e0a6f6c4f1e9d4b7a2e1c0f3a55",
  "status": "delivered",
  "delivered_at": "2026-10-23T13:00:04Z",
  "message_ids": ["1301234567890123456"],
  "message_url": "https://discord.com/channels/111/222/1301234567890123456",
  "error": null
}
```

`status` is `queued`, `sending`, `delivered`, `failed` or `unknown`. `failed` includes an error with `delivery_state`. `unknown` means the relay sent a request to the platform but could not confirm the result (for example a timeout); the relay must not retry it on its own.

### DELETE /deliveries/{idempotency_key}

Cancels a delivery that is still `queued` (returns 204). For a delivered message, deletes the posted message(s) only if the destination lists the `delete_message` option; otherwise 409 `not_cancellable`. Used only after an explicit user action in Rails.

## Pull mode: endpoints Rails provides

Base: `{PUBLIC_BASE_URL or private Rails URL}/integrations/{plugin_id}/relay/v1`.

| Method / path | Purpose |
|---|---|
| `PUT /destinations/{destination_id}` | The relay reports the destination's display name, `can_post`, `problem`, limits and options (the same body as push mode's GET response). Required before the first delivery and at least daily. |
| `GET /deliveries?limit=20` | Returns up to `limit` due deliveries for this link's destinations, each in the POST body format above plus `lease_expires_at`. Fetching leases them for 120 seconds; leased deliveries are not returned to another poll until the lease expires. Long-poll: waits up to 25 seconds when nothing is due. |
| `POST /deliveries/{idempotency_key}/result` | Reports the outcome in the GET delivery format above. Idempotent: repeating an identical result returns 200; a different result for a finished delivery returns 409. |
| `POST /deliveries/{idempotency_key}/extend` | Extends the lease by 120 seconds while a large upload is in progress. |

If a lease expires without a result, Rails cannot know whether the relay posted, so the delivery becomes `unknown` and is reconciled, never handed out again automatically. A relay that restarts mid-delivery must report `unknown` (or `delivered`, if it can confirm) for leased deliveries, and must not repost them.

## How Rails maps the protocol

| Rails step | Push | Pull |
|---|---|---|
| Connect | Owner enters relay URL, destination ID and relay token; Rails calls GET destination | Rails issues a pull token for the link; owner configures the relay; the relay calls PUT destination |
| `publish` | POST delivery: 200 delivered → published; 202 → pending, poll after 5 seconds | Mark the delivery due → pending; it appears in the relay's next poll |
| `reconcile` | GET delivery | Read the result the relay reported |
| delivered | published, with message URL | published, with message URL |
| failed, `not_submitted` | normal retry policy | normal retry policy |
| failed `submitted` / `unknown`, or lease expired | needs_attention (publication_unconfirmed) | needs_attention (publication_unconfirmed) |
| No result before `PROVIDER_PENDING_TIMEOUT_SECONDS` | needs_attention (publication_unconfirmed) | needs_attention (publication_unconfirmed) |

Rails produces media variants that fit the destination's reported limits before the delivery is created (02, FFmpeg variants). If a declared-protected image (07) exceeds the limits, the target is blocked with `protected_media_incompatible`.

Relays report no post metrics in v1; the Insights panel shows only tracked-link clicks for these destinations (09).

## Conformance tests

Both relays must pass a shared test suite run against them by Rails CI (push) or by a Rails test double (pull):

- Token required on every call; another link's token is rejected with 404 for its destinations.
- A repeated POST with the same key never posts twice; a different body with the same key returns 409.
- Media hash mismatch fails with `attachment_hash_mismatch`, `not_submitted`.
- A relay restart during sending reports `unknown` rather than reposting.
- Pull: leases expire, results are idempotent, an expired lease never reissues the delivery.
- Limits reported by the destination are enforced by the relay as well as by Rails.
- Unknown request fields return 422.

## Data in Rails

Tables are defined in 08: `relay_deliveries` (one row per delivery with mode, lease and reported result) and `integration_tokens` (digests of pull-mode tokens). Destinations are `social_accounts` with plugin `discord_yagpdb` or `telegram_bot`; the relay URL, destination ID and relay token are in the account's encrypted credentials.
